Evaluacion de decisiones cerradas, ambiguedades, riesgos y condiciones necesarias para comenzar la implementacion.

Analisis funcional y tecnico - Agosto de 2026

1. Resumen ejecutivo

El cuestionario contiene 253 preguntas funcionales. Se respondieron 63 y quedaron 190 sin respuesta. Dentro de las respuestas existen al menos 8 casos expresamente ambiguos (por ejemplo, “no entiendo”, “que numero” o una respuesta “si” que no selecciona entre dos alternativas).

Conclusion: hay informacion suficiente para comenzar el nucleo economico de las operaciones y preparar la arquitectura, pero todavia no para implementar de punta a punta certificados, anulaciones, cobranzas, plan financiero y Curva S.

La recomendacion es iniciar una Fase 0 de modelo base y cerrar antes seis decisiones bloqueantes. Empezar directamente con todo el modulo obligaria a inventar reglas que luego pueden alterar tablas, saldos e historiales.

3. Cambio principal respecto del prompt original: moneda libre

El PDF establecia USD. El Excel cambia esa decision: el usuario carga numeros en la moneda que desee, sin conversion ni cotizacion.

Riesgo alto: almacenar solamente “1000” sin moneda impide saber si son USD, ARS u otra divisa. Tambien vuelve incorrectos los totales, saldos y la Curva S si se mezclan monedas dentro del mismo proyecto.

Recomendacion minima, aun sin hacer conversiones:

  • Agregar moneda_codigo al proyecto o contrato financiero: ARS, USD, EUR, etc.
  • Todos los importes de un proyecto usan esa moneda.
  • El sistema no convierte; solamente muestra el simbolo/codigo correcto.
  • No permitir cambiar moneda cuando ya exista un certificado o movimiento.

Si se desea absoluta simplicidad, la mejor regla es: una moneda por proyecto. “Solo numeros” sin identificar moneda no es recomendable para datos financieros.

4. Precio y costo despues de certificar

La respuesta indica que, si el valor cambia, el certificado siguiente conserva el porcentaje anterior pero calcula el nuevo delta con el precio nuevo.

Certificado siguiente = (pct_nuevo - pct_anterior) x precio_vigente_nuevo

Esta regla es viable. Sin embargo, debe distinguirse entre:

  • Valor actual de Operacion: usado para certificados futuros.
  • Valor aplicado en un detalle emitido: fotografia del valor que produjo ese importe historico.
Recomendacion: el cambio de precio no recalcula documentos anteriores. Cada detalle guarda precio_aplicado e importe. El siguiente certificado usa el valor nuevo solo para el delta pendiente.

Aunque la respuesta dice “no congela el precio”, tecnicamente el documento emitido debe conservar el precio que utilizo. De otro modo, al consultar el certificado antiguo aparecerian montos diferentes de los emitidos.

5. Responsable operativo y financiero

Se respondio que el responsable financiero no necesariamente coincide con el operativo. Esto introduce una entidad o referencia adicional que no estaba cerrada:

  • responsable_id: quien ejecuta la operacion.
  • contraparte_pago_id: persona o empresa a quien se certifica y paga.

Antes de modelar certificados a contratistas debe decidirse si la contraparte financiera sera:

  1. otro registro de ResponsableOperacion;
  2. un Proveedor existente;
  3. una nueva entidad ContraparteFinanciera;
  4. un responsable de tipo especial con datos fiscales.
Mi recomendacion es reutilizar o ampliar ResponsableOperacion solamente si puede representar correctamente razon social, identificacion y datos de pago. Si no, crear ContraparteFinanciera y relacionarla con el responsable operativo.

6. Avance historico y fecha de corte

La respuesta “la fecha representa ejecucion efectiva o momento de carga: SI” no resuelve cual fecha manda. Para certificar historicamente se necesitan ambas:

  • fecha_efectiva: cuando ocurrio el avance.
  • fecha_registro: cuando se cargo en el sistema.

Para una fecha de corte debe tomarse el ultimo avance vigente cuya fecha_efectiva sea menor o igual al corte. Las cargas retroactivas realizadas despues pueden cambiar un preview, pero nunca deben modificar un certificado ya emitido.

“Avance de referencia” significa el porcentaje fisico que el sistema mostro al emitir. Conviene guardarlo en el detalle para poder explicar posteriormente:

avance fisico de referencia 75% - porcentaje certificado 60% = diferencia -15%

8. Contradicciones y riesgos

  1. Certificar sin precio o costo: si el valor es cero, se puede emitir un certificado de importe cero. Debe decidirse si eso es informativo o un error.
  2. Fecha futura: un corte futuro no puede conocer avance futuro; solo puede usar avances registrados hasta el momento de generar el preview.
  3. Operaciones posteriores: se respondio que no se incluyen porque la fecha “corta”, pero una fecha no implica secuencia. Debe aclararse si el corte por fecha filtra por avance historico o tambien por orden de operaciones.
  4. Redondeo a un decimal: es adecuado para visualizacion, pero almacenar dinero con un solo decimal puede acumular diferencias. Se recomienda almacenar cuatro decimales y mostrar uno.
  5. Borrado de certificados: contradice la trazabilidad exigida para cambios de precio y el caracter financiero de los documentos.
  6. Responsable financiero distinto: contradice la idea simplificada de seleccionar al responsable de la operacion como contratista a pagar.

11. Seis decisiones bloqueantes antes de programar certificados

  1. ¿Se acepta una moneda identificada por proyecto, aunque no haya conversion?
  2. ¿Fecha de corte usa fecha efectiva del avance y el ultimo evento menor o igual?
  3. ¿Quien es exactamente la contraparte financiera cuando difiere del responsable operativo?
  4. ¿Se permiten porcentajes menores al certificado anterior o mayores a 100%?
  5. ¿Un certificado emitido se anula con trazabilidad o se borra fisicamente?
  6. ¿Como se corrige un certificado si ya existen certificados posteriores?

12. Recomendacion para comenzar

SE PUEDE INICIAR la Fase 0:

  1. Confirmar el esquema real de AvanceOperacion y sus fechas.
  2. Agregar moneda del proyecto sin conversion.
  3. Agregar precio y costo actuales en Operacion.
  4. Crear auditoria de cambios economicos.
  5. Diseñar las cabeceras y detalles de certificados sin ejecutar migraciones definitivas.
  6. Construir casos de prueba del delta y cambio de precio.

NO INICIAR TODAVIA cobranzas, pagos, anulaciones, plan financiero y Curva S hasta responder las seis decisiones bloqueantes y las secciones pendientes correspondientes.

Valoracion final: las respuestas simplifican bien el alcance, pero introducen dos cambios estructurales importantes: moneda libre y separación entre responsable operativo y financiero. Cerrando esos puntos y las reglas de correccion, el nucleo de certificaciones puede comenzar con una base estable.

Este documento interpreta las respuestas del Excel y señala recomendaciones. No modifica el proyecto ni constituye una migracion aprobada.
